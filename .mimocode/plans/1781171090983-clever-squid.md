# 个人天赋发掘测评系统 — 代码逻辑与架构优化计划

## 概述

本计划从 **安全、性能、代码质量、架构设计** 四个维度梳理项目优化点，按优先级分 3 个阶段实施。

---

## 阶段一：高优先级（安全 & 关键架构问题）

### 1.1 模板导航栏/ Footer 去重 → Jinja2 片段复用

**问题**：8 个模板文件各自复制粘贴了 ~20 行导航栏 + ~40 行 Footer，修改一处需同步 8 个文件。

**方案**：
- 在 `templates/` 下新建 `_nav.html` 和 `_footer.html` 两个片段模板
- 各页面用 `{% include '_nav.html' %}` 和 `{% include '_footer.html' %}` 替换内联代码
- 涉及文件：`index.html`, `report.html`, `scale.html`, `dictionary.html`, `history.html`, `talent_type.html`, `login.html`, `register.html`

### 1.2 XSS 修复 — innerHTML 消毒

**问题**：`dictionary.js`, `scale_result.js`, `talent_type_result.js`, `talent_type.js` 等文件直接用 innerHTML 插入 API 返回数据，未经 `escapeHtml()` 处理。`marked.parse()` 输出也直接 innerHTML 注入。

**方案**：
- 在 `static/js/` 下新建 `utils.js`，导出 `escapeHtml()` 函数（复用 `main.js` 中已有的实现）
- 所有 JS 文件的 innerHTML 插入点改为先经过 `escapeHtml()` 处理
- 引入 DOMPurify（CDN），对 `marked.parse()` 输出做消毒：
  ```js
  contentEl.innerHTML = DOMPurify.sanitize(marked.parse(md));
  ```
- 涉及文件：`dictionary.js`, `scale_result.js`, `talent_type_result.js`, `talent_type.js`, `report.html`, `history.html`

### 1.3 量表结果从 localStorage 迁移到服务端获取

**问题**：`scale_result.js` 完全依赖 `localStorage.getItem('scaleResult')` 展示结果，清除浏览器数据或换设备即丢失。

**方案**：
- `scale_result.html` 改为从 URL 参数获取 `session_id`
- 新增 API `GET /api/scale/result/<session_id>` 从数据库查询结果
- `scale.js` 提交成功后跳转 `/scale/result?session_id=xxx`
- 涉及文件：`routes/scale.py`, `static/js/scale.js`, `static/js/scale_result.js`, `templates/scale_result.html`

### 1.4 `report` 路由添加 `@login_required`

**问题**：`routes/main.py` 的 `/report` 路由访问了 `current_user.id` 但缺少 `@login_required`，未登录用户会触发 `AttributeError`。

**方案**：添加 `@login_required` 装饰器。文件：`routes/main.py:14`

### 1.5 管理后台 N+1 查询修复

**问题**：`routes/admin.py` 的 `get_records` 和 `get_users` 存在严重的 N+1 查询（对每条记录逐一查用户），1000 用户 × 10 测评 = 30000+ 次查询。

**方案**：
- `get_records`：使用 `db.session.query(InterviewSession, User).join(User)` 替代循环内查询，将排序和分页交给数据库（`ORDER BY ... LIMIT ... OFFSET ...`）
- `get_users`：使用子查询一次获取每个用户的测评计数
- 涉及文件：`routes/admin.py`

## 阶段二：中优先级（代码质量 & 一致性）

### 2.1 统一 API 错误响应格式

**问题**：不同路由的错误响应格式不一致：`admin.py` 返回 `{"error": "..."}`, 其他返回 `{"success": False, "error": "..."}`。

**方案**：定义统一的错误响应辅助函数，所有 API 统一使用 `{"success": bool, "error": str}` 格式 + 正确的 HTTP 状态码。

### 2.2 内联 CSS/JS 外迁

**问题**：
- `talent_type.html` 内嵌 ~290 行 CSS（与 `style.css` 中 `tt-*` 类重复）
- `talent_type_result.html` 内嵌 ~220 行 CSS
- `history.html` 内嵌 ~455 行 JS

**方案**：
- 将 `talent_type.html` 和 `talent_type_result.html` 的内联 CSS 合并到 `style.css`，删除重复定义
- 将 `history.html` 的内联 JS 提取到 `static/js/history.js`（已有此文件但内容为空或不完整，需确认）
- 涉及文件：`templates/talent_type.html`, `templates/talent_type_result.html`, `templates/history.html`, `static/css/style.css`, `static/js/history.js`

### 2.3 InterviewSession 创建逻辑去重

**问题**：`routes/interview.py` 中 `_get_or_create_interview`（第 11-23 行）和 `start_assessment`（第 58-70 行）有几乎相同的创建逻辑。

**方案**：提取 `def _create_interview(user_id)` 辅助函数，两处复用。

### 2.4 system prompt 模板化

**问题**：`services/ai_service.py` 的 `get_system_prompt` 方法长达 117 行，`is_first_round` 两个分支有大量重复文本。

**方案**：
- 将公共部分（四段式输出格式、禁止列表等）提取为常量字符串
- 使用 Jinja2 或 `.format()` 模板化 system prompt
- 涉及文件：`services/ai_service.py`

### 2.5 全局错误处理器

**问题**：项目缺少 `@app.errorhandler(404)` / `@app.errorhandler(500)` 全局处理。

**方案**：在 `app.py` 中添加 404 和 500 错误处理器，API 请求返回 JSON，页面请求渲染错误模板。新建 `templates/404.html` 和 `templates/500.html`。

### 2.6 `datetime.now` → `datetime.utcnow` 或 `func.now()`

**问题**：所有模型的 `default=datetime.now` 使用本地时间，跨时区部署会不一致。

**方案**：统一改为 `default=datetime.utcnow` 或 SQLAlchemy 的 `func.now()`。涉及文件：`models.py`

### 2.7 JSON 反序列化加异常处理

**问题**：`routes/history.py` 多处 `json.loads()` 无 try-except，数据库中 JSON 损坏会导致页面崩溃。

**方案**：统一用 try-except 包裹，损坏数据返回空值或默认值。

### 2.8 答案数据服务端校验

**问题**：`routes/scale.py` 不校验答案值范围（应为 1-5）、题目数量、题目 ID 合法性。

**方案**：在 `submit_scale` 中添加校验逻辑，非法数据返回 400 错误。

## 阶段三：低优先级（优化 & 清理）

### 3.1 `before_request` 访问追踪优化

**问题**：每个页面 GET 请求执行一次 `db.session.add()` + `db.session.commit()`，高并发下性能差。

**方案**：改为内存缓冲 + 定时批量写入（如每 60 秒或累积 50 条后 flush）。

### 3.2 量表添加反向计分题

**问题**：`scale_data.py` 所有 20 题的 `reverse` 均为 `False`，用户可无脑全选 5 分刷高分。

**方案**：每维度至少 1 题设为 `reverse: True`，计分时反转。

### 3.3 计分平局处理

**问题**：`talent_type_data.py` 的 `calculate_type_code()` 中 `max()` 遇平局时默认选第一个维度，用户无感知。

**方案**：检测平局情况，在结果中标记存在歧义的维度，或提示用户补充作答。

### 3.4 清理遗留代码和调试日志

- `routes/main.py:2` 移除未使用的 `session` 导入
- `static/js/scale.js` 移除 `console.log` 调试日志
- CSS 响应式断点统一为 640px / 768px / 1024px

### 3.5 `config.py` 收归分散配置

- `app.py:18` 的 `SQLALCHEMY_DATABASE_URI` 移入 `Config` 类
- `app.py:126-127` 的 `HOST`/`PORT`/`DEBUG` 移入 `Config` 类

### 3.6 完善天赋类型学详细报告覆盖率

**问题**：`DETAILED_REPORTS` 仅覆盖 15/72 种类型，其余使用模板生成的默认报告。

**方案**：逐步补充剩余 57 种类型的详细解读报告。此为内容工作，可后续迭代。
